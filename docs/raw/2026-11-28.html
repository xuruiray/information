It was only today that I understood one of its most attractive characteristics. Normally, if you want to grab a snapshot copy of a SQLite database, you need to use either the backup API or VACUUM INTO . In both cases you need enough disk space to create a duplicate copy of your database, so if you're on a small instance and you already use more than half of the available disk you are plain out of luck. sqlite3_rsync can copy a snapshot of your database over an SSH connection to another machine, without first needing to create a full local copy! It's also good for synchronizing an existing copy of a database without re-transmitting the entire thing over the network. It works in a similar way to regular rsync: The core idea behind the protocol is that the replica sends cryptographic hashes for pages or groups of pages over to the origin side. The origin sends back page content that differs, or requests finer-grain hashes if a multi-page hash does not match. If the origin and replica start out being vastly different, the total network bandwidth can exceed the size of the entire database, due to the overhead of exchanging hashes, but the excess bandwidth is not great - a few percent at most. Read more 85 Workflow is 10x faster, again Workflow SDK 5.8 runs workflows on a new execution engine, rebuilt for performance. Step-to-step latency is 12x lower, and large fan-outs, like running 256 steps in parallel, use 14x less function time outside your step code. This directly improves turn times for durable AI agents, among many other improvements.To get the new engine, upgrade to workflow@5.8.0 or later. New runs will use the new engine by default, and runs already started on an older version will safely keep running on that version. Make sure your steps are idempotent where possible to get the most out of this upgrade.Drastically reduced overheadIn our benchmarks comparing 5.2.0 to 5.8.0, p75 step-to-step overhead fell from 85 ms to 7 ms. The median run, including 102 seconds of step work, finished in 111 seconds instead of 3.0 minutes. Running 256 parallel steps in a fan-out added 5.5× less overhead, 2.5 seconds instead of 13.5 seconds, and the median run spent 14× less time in functions beyond the steps' own work, 105 seconds instead of 1,446. A five-turn agent loop that streams its tokens through durable streams and calls tools added 0.9 seconds of overhead instead of 3.0 seconds, 3.3× less. Consult the benchmarks page for how we measure these numbers.Resuming after 1 second idle time went from 425 ms to 184 ms, 2.3× faster. Resumptions more than 5 seconds out might see slightly larger overhead. You can choose to keep functions warm for longer to optimize time-to-resume at the cost of additional compute time.Speculative execution for retryable stepsMany of the above benefits rely on speculative execution of Steps. Only Steps that are idempotent can be run in this way. A step that passes its stepId as an idempotency key, like the Stripe charge below, is already safe and needs no changes. If your step is sensitive and can't be retried, mark it with maxRetries = 0 to opt out and ensure it still runs at most once.You should already be making Steps idempotent wherever possible, or flag them with maxRetries = 0, to ensure Workflow SDK doesn't re-run your Steps when it's not safe to do so.Get startedUpgrade to workflow@5.8.0. To keep creating runs on the previous engine after upgrading, set WORKFLOW_SPEC_VERSION=8. If you're on 4.x, start with the upgrade guide, since v5 is a major release.Using a third-party World? All Worlds maintained by Vercel already support the new engine. A third-party World needs to support World spec version 9 before upgrading gives you any of these improvements. Until it does, new runs keep using the previous engine.
